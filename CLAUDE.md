# Party Item Manager

Shared D&D party inventory tracker. Five party members (Yiptik, Radish, Tuffany, Astrielle, Hyrroh) plus Senchez, a sentient bag of holding, tracked as a sixth "holder".

## Architecture

- **Frontend**: React 19 + TypeScript + Vite, in `src/`. No router — one screen with a scope selector (`Sidebar`) and orthogonal filters (`FilterBar`). The item UI is split across `ItemList.tsx` (grouping/folds), `ItemRow.tsx` (plaque + send/disposal/pack/fill dialogs, exports `ItemListProps`), `ItemDetail.tsx` (detail view + journal entries), `ItemEditor.tsx`, `RollDialog.tsx`, and `Tumbleweed.tsx`.
- **Storage (current)**: browser localStorage via `src/api.ts`, which implements the full domain logic (moves/merges, gold, change log) client-side. The app is a pure static site; GitHub Pages deploys it on every push (`.github/workflows/deploy.yml`).
- **Backend (dormant)**: `server/` keeps the original Express API + JSON-file store + optional password login. To revive shared storage, restore the fetch-based `src/api.ts` from git history (commit 7fcebd2) — component code is unchanged either way. `npm run server` runs it.
- **Sync**: the frontend polls `getState()` every 10 s and re-fetches after each mutation; with localStorage this keeps multiple tabs of the same browser in sync.

## Commands

- `npm run dev` — Vite dev server (:5173).
- `npm run build` — typecheck (`tsc --noEmit`) then `vite build`. **Run this before committing frontend changes.**
- `npm run typecheck` — typecheck only.
- `npm run preview` — serve the production build locally.
- `npm run server` — the dormant Express backend (only relevant if shared storage is revived).
- `npm run smoke` — builds, then drives the real app in Chromium through the party's flows (add, move, sell, long rest with rolls/perishables/supper, compendium, log filter, passing the torch). **Run this before pushing anything structural, especially changes to `src/api.ts`** — it's the safety net for the move off localStorage. Point at another browser with `CHROMIUM=/path/to/chrome`.

`npm run smoke` is the automated test; verify changes with `npm run build` at minimum and `npm run smoke` for anything touching domain logic.

## Domain rules encoded in the app

- Holder ids are fixed: `yiptik`, `radish`, `tuffany`, `astrielle`, `hyrroh`, `senchez` (`HOLDERS` in `src/types.ts`; the dormant `server/index.js` has a matching `MEMBER_IDS` — keep them in sync if the server comes back).
- Moves can split stacks (qty < stack) and auto-merge with a same-name/type/rarity stack at the destination (`moveItem` in `src/api.ts`) — except when either side has journal entries (never merged; a split-off copy leaves entries behind).
- Journal entries: any Information-category item (`canJournal` in `src/types.ts`) collects dated `entries` (`JournalEntry`: optional title, text, optional compressed sketch — text or sketch required). Managed straight from the detail view (`EntriesSection` in `ItemDetail.tsx`, add/edit/tear-out via `addEntry`/`updateEntry`/`deleteEntry` in `src/api.ts`, all logged); entry text/titles are searchable, and a collapsed plaque previews content → latest entry → notes, in that order. Information is also the only category that can be *copied* rather than handed over: the send menu on a papers item shows a "➤ Hand it over / 📋 Send a copy" chip pair (`canCopy` in `ItemRow`, heading flips to "Copy for"), and `copyItem` in api.ts drops a qty-1 duplicate on the recipient — name suffixed "(copy)" unless it already is, `attuned` cleared, and every journal entry re-idded so the two transcriptions diverge from there. The original never moves. Logged as "copied X for Y 📋". Deeds are the exception: a deed is an instrument, not just words, so its copy files as subtype `note` (icon override dropped with it), the chip reads "📋 Send a transcript" over a "Transcribe for" heading, and the log says why — only one thing in the party is ever the deed.
- Attunement: max 3 per member (warning only, not enforced); moving an item into Senchez clears `attuned`.
- "Magic" for filtering = `magic` flag OR `requiresAttunement` OR rarity above common (`isMagic` in `src/types.ts`).
- Stack values are per item, and both the compact tag and the full row say which: `valueParts` in `types.ts` renders "1,000 gp ea." on plaques and printed tag rows and "1,000 gp each · 2,000 gp total" in detail rows (totals gp-equivalent, so "5 pp each · 150 gp total"), leaving prose values ("priceless") exactly as typed. Item taxonomy: items carry `category` (gear / accessory / consumable / arcana / supplies / papers [shown as Information 📜] / treasure 👑 / other, `CATEGORIES` in `src/types.ts`) plus an optional `subtype`; `CategoryPicker` is a progressive wizard: picking a category collapses the others and reveals subtypes ('none of these' skips), including `CROSS_LINKS` pointer chips marked ↪ for subtypes people hunt for in the wrong place (Arcana → scroll/potion, Gear → wand/staff, Papers → scroll) that file the item under its real home, picking a subtype collapses the rest, and only then does the add form reveal its fields (`adv.catDone` gates them); chosen chips tap back a stage. Each category/subtype has a form plan (`formPlan` in `src/types.ts`): primary fields show up front, the rest sit behind a "More options" toggle, and fields in neither list are hidden and scrubbed on save (papery subtypes drop weight/attunement, food drops attunement/value-by-default, gems lead with value). Papery items get a `content` field ("what's written on it", searchable, shown as a quoted block in the detail view) with notes relabeled "What it looks like". Photos attach in the builder and the editor.
- Inventory grouping: a holder's tab groups items under category headers (taxonomy order, empties omitted, `byTaxonomy` sort by category/subtype/name; uncategorized last); the Everything view has a By holder / By category toggle (remembered in localStorage `pim-all-mode`): holder mode keeps holder groups with the same sort inside; category mode uses the category headers with party-wide weight totals and a right-aligned holder chip on every row.
- Potion rolling: consumables with a `heal` formula ("2d4+2") intercept "Use one" with a dialog — roll in-app (DM-Screen's ported SVG dice tumble in `src/components/Dice.tsx`, parser in `src/dice.ts`) or roll your own (no animation); in-app results land in the change log via `consumeItem`'s note param. Seed and load-time migration backfill stats from the catalogue by name.
- Item stats: `item.stats` (`ItemStats` in `src/catalog.ts`) holds type-specific mechanics; `statPlan` in `src/types.ts` decides which stat controls each type shows (weapons: damage/type/bonus; armor: AC/weight class; accessories: AC rider advanced; staffs/rods: weapon damage advanced; potions: heal primary + dmg/DC advanced; wands/staves/rods: charges with spend/recharge actions plus a freeform `spells` list (one per line, cost last — `parseSpellLines` in `src/dice.ts`) whose per-spell Cast buttons spend that cost via `castSpell`, disabled when charges run short; scrolls: a single `spell` name up front (`SpellNameField` in StatFields.tsx — compendium autocomplete chips, a live ✓/? mark, free text accepted for homebrew/paywalled names) plus level/DC; the detail view's Spell row links `stats.spell` straight to its card and only falls back to the name-derived `findSpellForItem` when it's unset; containers: capacity; papery: language; cursed rides with magic). `StatFieldControl`/`cleanStats` in `src/components/StatFields.tsx` render and scrub them. The catalogue is enriched with DM-Screen's weapon/armor/charge data (118 entries). `classifyLegacy` maps the old flat `type` strings (and "wondrous item" by name) — `migrateTaxonomy` in `src/api.ts` applies it to stored items and custom entries on load; keep the copy of the classifier in any catalog-regeneration script in sync.
- Printable sheet: every holder tab (Senchez included) carries a quiet 🖨️ in the lower-right corner, the same fixed-corner slot Home gives the 📖 compendium (they never coexist — the book is Home-only, the press is holder-only). It opens a self-contained HTML document in a new window rather than navigating away: `sheetHtml`/`writeSheet` in `src/print.ts`, a lazy `import()` chunk (~4 KB gz) so nobody pays for it until they print. The window must be opened synchronously inside the click (a popup blocker eats it otherwise) and is handed to `writeSheet` already open, showing "Setting the press…" until the chunk lands. The sheet groups by category in taxonomy order with per-group counts and weights, leads with a header (item count, carried weight, date) and a purse line mirroring `PursePanel` (gp, pp with its gp conversion, qty-aware gems minus set-aside). Two densities share one document and toggle by a class on `<body>`: Normal is the collapsed plaque's information (icon, name, qty, tag row, preview line) and Detailed reveals the expanded card's rows plus pack contents, spell lists, quoted `content`, notes, journal entries, and pictures — the item photo rides in a fixed column beside the rows (`.det` is a flex row; portrait shots shrink to a max-height rather than running down the page) and journal sketches sit inline under their entry, both straight from the stored data URLs, both sized down again under `@media print`. Normal folds all of it away, so the toggle never re-renders or loses scroll. Each row gets a tick box for counting by hand, values that are set aside carry 🔒, and `@media print` tightens type and spacing (the screen keeps the roomier version). Printing while a filter is on prints what you see and says so on the page.

- Carrying weight: optional per-holder limit (`carry` in state, absent = nobody's counting, which is the default for everyone). Set from `RenameDialog` — a "⚖️ Carrying limit (lb)" field under the food toggle, blank to stop counting — via `setCarryLimit` in api.ts, logged both ways. Offered on every holder including Senchez (his homebrew limitlessness is just the default, not a rule the app enforces). When set, the inventory heading grows a `⚖️ 112/500 lb` line above the attunement line (`carryState` in App.tsx, `weighItems` in types.ts sums qty × weight and ignores weightless items), turning red with "· over encumbered" past the limit; the printed sheet's header switches to "112/500 lb carried" to match. The add form warns before you commit — `weighIn` prop → `load` in `AddItemForm` projects current + (weight × qty) and shows a red `.carry-note` when the add would land the holder over ("this would put them 26 lb over") or when they already are ("already over encumbered"). It is only ever a nudge: nothing disables Add, and no other operation (moves, edits) checks weight at all.
- Senchez has no weight limit (homebrew bag) — the rail badge and category headers show carried weight as information only.
- Party money: per-holder integer gp and pp (`gold`/`platinum` in state, 1 pp = 10 gp via `PP_IN_GP`). All displayed totals are gp-equivalent. `setPurse` sets a purse outright, `addMoney` adds coins, `spendMoney` subtracts, `transferMoney` moves them, `splitMoney(from, gp, pp, actor)` divides a pile evenly among the five `MEMBERS` — `from: null` means the coins are new to the party (the Add-coins dialog and Home's "Give gold to…"), so nothing is deducted and the log reads "added X and split it"; a HolderId deducts from that purse first — each coin type on its own (7 pp among five is 1 pp each with 2 pp over), the sender taking a share like everyone else, and every remainder landing in Senchez rather than being rounded away (when the bag is the one splitting, the log says it "stays in the bag"); all take (gp, pp) so both coins move in one logged action, and every Add/Spend/Send form (`CoinDelta` in App.tsx, `GiveForm` in GoldTracker) shows a gp field and a pp field side by side. Coins NEVER convert — table rule: platinum doesn’t break into gold — so each coin type is checked against its own supply (`checkPurse` in api.ts; the overdraw error adds "platinum doesn’t break into gold" when spare pp exists). Typing "25 gp" / "3 pp" into the quick-add box routes to `addMoney` instead of creating an item (`parseMoney` in `AddItemForm`).
- Purse panel (`PursePanel` in `App.tsx`): every holder tab (Senchez included) shows a collapsed "🟡 N gp" line (coins-worth only, shown even at zero, with a 💎 count hint); tapping expands rows for gold, platinum (with gp conversion), gems, and a Total-worth line, plus ＋ Add / − Spend / ➤ Send (send shows an item-style holder grid — every recipient plus a dashed "🤝 Split among party" — then the shared `CoinDelta` form; `transferMoney` moves the coins in one logged step, `splitMoney` divides them). `CoinDelta` takes an optional `preview(gp, pp)` render prop, which the split uses to work the shares out live as you type ("20 gp + 1 pp each to all 5 · 3 gp + 2 pp over to Senchez") and to explain itself before anything is typed; `GiveForm` in GoldTracker takes a plain `note` for the same purpose. The split is offered in all four places coins choose a destination — both send grids, the 🪙 Add coins dialog's `<select>`, and Home's "＋ Give gold to…" `<select>` — and the division itself lives in `splitShares` (types.ts) so the live preview and the coins api.ts actually moves can never disagree. and `CoinStream` takes a list of recipients so a split fans coins to all five rail tabs at once and a ✎ exact-amount editor. A successful send fires `CoinStream` (in `App.tsx`): coins fly from mid-screen to the recipient's rail tab, located via the tab's `data-scope` attribute. The gems row is derived from treasure/gems items: values parsed by `parseGoldValue` in `types.ts` (qty-aware; prose values don't count), and gems with `fungible: false` ("Counts toward gold total" checkbox in the gems form plan, default on) are listed as "set aside" and excluded from worth — the detail view marks them "🔒 set aside". The Home party-gold number stays hard coins only.
- Disposal: both discard triggers (corner 🗑 and the send-menu Discard) open a dialog — Ate/drank or Used up (consumables only, see below), Sold (amount + gp/pp, `sellItem` removes the item and pays its holder in one logged step), Discarded/lost, Destroyed, Given away (an NPC — instant, logged as "gave X away 🎁" — or a party member, which hands off to the regular send flow), Cancel. `deleteItem` takes a disposition ('lost' | 'destroyed' | 'given') for the log line. Each fate has its own plaque exit animation (`exit-sell/toss/destroy/gift` in styles.css); `dispose()` in `ItemRow` delays the actual mutation ~520 ms so the exit can play. Stacks get a qty stepper in the dialog (default 1, "all N" shortcut, `takeFromStack` in api.ts shrinks or removes); a partial disposal plays a brief `exit-part` blip instead of the full exit since the plaque stays.
- Consumed as a fate: the disposal dialog's first option appears only when `category === 'consumable'` — "🍽️ Ate / drank it" for food & drink, "🧪 Used it up" for everything else consumable (`eaten` in `ItemRow` is just `isFood`). Food and drink deliberately share one subtype and one label: nothing in the app behaves differently for the two, so nobody is made to declare which a thing was. It routes to `consumeItem`, which now takes a `qty` (one act, one log line, and one empty vial per potion) — so this and the send menu's "Use one" write identical history; "Use one" stays the front door for drinking a single potion, since it alone intercepts `stats.heal` with the roll dialog. Exits: `exit-eat` bites the plaque away from the right in five `steps(1)` snaps with a jolt on each (clip-path polygons cut the scalloped edge), `exit-dissolve` blurs and fades. Eating part of a stack downgrades to `exit-nibble` instead of the usual `exit-part` blip — one bite snaps out of the edge, the plaque flinches, and it closes up again, because five apples are still there. Every consume plays an exit, wherever it was triggered: "Use one" in the send menu and the detail view, the disposal dialog, and the potion roll dialog (both "roll it here" and "roll my own") all route through `dispose`, which takes an explicit qty and delay so callers other than the dialog can use it — so the last crust is bitten away, one of six is nibbled, and a potion dissolves rather than blinking out. The roll path passes a 650 ms delay so the +HP float still has a plaque to rise from.
- Liquid vessels: containers (supplies/container, minus equipment packs) hold a `liquid` ({name, doses}); the detail's Contains row offers Use 1 (dose down, last one empties it) / 🫗 Empty (confirm) when full, and 🫗 Fill… (name + dose count dialog) when empty. Collapsed plaques preview the contents, search matches liquid names, and stacks never merge when either side holds liquid. Drinking any consumable/potion leaves an empty "Vial" behind (merged into an existing empty Vial stack) via `consumeItem`; `fillContainer`/`emptyContainer`/`drinkFromContainer` in api.ts all log.
- Equipment packs: catalogue packs carry a `pack` list ({name, qty}[], names resolving back to the catalogue); created/stored pack items get it via `createItem`/load-time backfill. The detail view lists remaining contents with a ➤ per row (dialog: take out here / send to a holder — with the flight ghost — / discard; whole entries only) and a 📤 Unpack button (confirm, then `unpackItem` materializes everything into the holder's inventory and removes the pack). `takeFromPack`/`discardFromPack` shed the component's catalogue weight from the pack item. All logged.
- Ammunition: the detail view of any `ammunition`-subtype item swaps the Quantity row for an Ammo row (`AmmoRow` in `ItemDetail.tsx`): − Spend / ＋ Recover open a count form committing once via `adjustAmmo` in api.ts (one log line; spending the last removes the stack).
- Food freshness: `item.freshness?: number` plus `freshnessMax` (set on create; edits raise the max only when the new value exceeds it — a smaller value adjusts what's left; load-time migration backfills max = current). Any item can perish — a harvested liver, a body under Gentle Repose, a dated writ — via the "Keeps for (rests)" field in both forms (blank = keeps forever); `formPlan` wraps `basePlan` to append `freshness` to every plan's advanced tier, so it's primary only for food & drink and behind "More options" everywhere else. Wording follows `isFood` (types.ts): food spoils (🤢 / 🍏 / "Freshness"), anything else expires (⌛ / ⏳ / "Keeps until"). `FreshnessGauge` (in ItemDetail.tsx) renders the fraction as a bar whose fill and hue slide green → yellow → orange → red (`hsl(120·frac)`): mini next to the plaque name (collapsed and expanded, plus a tinted count tag when expanded), full-size in the detail's Freshness row ("N of M rests left"). Each long rest in that inventory ticks it down, except on the last day of a **single-day** clock (`freshnessMax === 1`): only those are genuinely ambiguous (24 hours of goodberries can outlast one 8-hour rest), so the first rest that would finish one asks instead — the decisions page offers Still good / Gone off per item, "still good" sets `graced` and buys exactly one more day, and the next rest settles it without asking. Editing the clock clears `graced`. Hitting 0 marks it spoiled (🤢 by the plaque name, sickly-green tag, "eat at your own risk" detail row) but never deletes it — players discard or risk it. Spoiled/expired items get a one-tap 🗑 Toss (whole stack, no confirm, `deleteItem`'s `'spoiled'` disposition and the usual toss exit animation) in the detail's Freshness row and beside Eat one on the rest's supper page — deliberately never on a collapsed plaque. Anything with a longer clock expires on schedule, announced up front: the rest preview has a line for what spoils overnight, a line for what will be asked about, and a countdown line that flags items down to their last day ("last day after this"). The result reports spoilage, and log lines record it ("the Fresh Apples spoiled 🤢" / "the rations age a day"). Stacks with freshness never auto-merge.
- Long rest: per-inventory only — each holder tab's heading (Senchez included) carries a faded 🌅 after the name; there is no party-wide rest (Home's corner holds just the 📖). The dialog (`LongRestDialog` in App.tsx) walks three stages: a preview explaining what resting will do (auto / your rolls / waiting on owners / already-full gear, listed once so nothing looks forgotten / rations aging / supper to come), then — only when there are dice recharges of yours — the roll page, then the supper page → `longRest(actor, holder, rolls?)` in api.ts recharges every under-charged item with `chargesMax` (scoped to `holder` when given), except consumables (their charges are doses). Items whose `recharge` text contains a dice formula (`findRoll`/`diceText` in `src/dice.ts`) belong to their owner and are NEVER auto-rolled: the dialog lists the presser's own dice items ("Playing as" match, plus Senchez's) each with a rolled-total field and an optional in-app 🎲 that tumbles the SVG dice inline under the row, filling the field when they settle; the totals pass through `longRest(actor, holder?, rolls?)` and blank fields stay uncharged (listed as waiting, like other owners' items). `recharge: "never"` (`neverRecharges` in dice.ts) marks finite supplies — beans, beads, wishes — which long rests skip entirely and whose ↺ Recharge button is hidden. The detail-view ↺ Recharge respects dice recharges too: it opens `RechargeDialog` (in `RollDialog.tsx`) — roll in-app or type what the real dice said — and `rechargeItem(id, actor, rolled?)` refuses to full-refill a dice-recharge item without a roll. The catalogue carries recharge data for all ~40 charged SRD items (dawn dice for wands/staffs, "never" for the finite ones); `migrateTaxonomy` backfills it onto stored charged items missing it. Preview and result share one dialog; one log line summarizes. The final stage is `SupperSection` (App.tsx): the inventory's food & drink items and filled vessels with one-tap 🍽️ Eat one (`consumeItem` with a "supper at camp 🍽️" note) / 💧 Drink 1 (`drinkFromContainer`), plus empty vessels with 🫗 Fill with water (doses from `stats.capacity`'s leading number, default 4). Missing food or drink is called out rather than silently omitted. A reminder only — deliberately no required amounts; spoiled food is listed with its 🤢. Characters who don't eat (warforged, constructs) are skipped entirely — `SupperSection` renders nothing for them and the preview says why. The toggle is a per-character setting, not a rest control: it lives in `RenameDialog` (tap the holder's name) as "🔩 Doesn't need food or water", between the spelling fix and the character-death link. State: `needsFood` (absent = eats, `eatsFood` in types.ts), written by `setNeedsFood`, logged. Senchez is hard-wired out of it — `eatsFood` returns false for `senchez` whatever `needsFood` says, the toggle is hidden on his rename dialog (members only, like the death link), and his preview gets its own line ("a bag, not a boarder") instead of the warforged one.
- Rest stamps: `lastRest` in state ({at, actor} per holder, absent = never) is written by every `longRest` with a holder — unconditionally, even when nothing needed recharging, since "did someone already?" is the question. Anyone can rest Senchez, so the preview opens with "Last rested {`sinceText`} by {actor}" (exact stamp in the `title`); under two hours old it turns gold and adds what a second rest would do (`restedRecently` in `LongRestDialog`). Shown for every holder, not just Senchez.
- Change log: capped at 500 entries, actor comes from the client's "Playing as" picker (localStorage). The Log tab filters: free-text search (matches text + actor) plus one-tap holder chips (`LogPanel`); old entries keep pre-rename names, so a chip only matches its current-name era.

- Home tab (default scope): the party-gold number (click for the ledger breakdown — tapping a holder row there opens ＋ Add / − Spend / ➤ Send / ✎ exact tools in `GoldTracker`, mirroring the purse panels; Send picks a recipient grid, routes through `transferMoney`, and fires the CoinStream), a quiet search field that searches the whole party (results grouped by holder), and the + Add pill. Adding everywhere goes through the same modal (`AddItemForm`); there is no inline add form. The search field (`FilterBar`) reveals type/rarity/magic controls only on focus or when a filter is active.
- Holder names: the six ids are permanent slots; display names are overridable per slot (`names` in state). `applyHolderNames` in `src/types.ts` stamps the overrides onto the `HOLDERS` entries at load time (deliberate module-state mutation, called from `load()` in api.ts), so every `h.name` read — rail, headings, send grids, log lines — shows the current character with no prop threading. Tapping the name in a holder's heading (no ✎ badge — quiet dashed underline on hover) opens `RenameDialog` (App.tsx): a plain rename for spelling fixes (`renameHolder`, logged), and behind a muted "💀 Character death…" link (members only, gated by a required "truly gone" checkbox so a typo fix can't wander into it) the passing-the-torch flow: `passTorch` sets the new name, ends attunements, clears portrait+icon, optionally sweeps all items and coins to Senchez, and writes a candle-lit eulogy log line. Old log entries keep the old name (stored text). If the renamer was "Playing as" the old name, App updates the actor picker to match.
- Holder icons: per-holder emoji stored in state (`icons`), editable from the holder's own tab via the heading icon (`IconPicker`); defaults live on `HOLDERS`. The phone rail shows icons only.
- Holder portraits: members only — Senchez wears his animated `SenchezFace` instead, so the portrait UI is skipped for him. Per-holder photo (`portraits` in state, compressed via `src/image.ts` like item photos) shown as a round avatar leading the inventory heading (`HolderPortrait` in `App.tsx`); no portrait → quiet dashed 📷 button that opens the file picker directly; tap the avatar to zoom with Replace/Remove (remove confirms). `setPortrait` in `src/api.ts` logs both.
- Party custom catalogue: items built through the custom-item wizard save to the catalogue by default, via a "✦ Save to the party catalogue" checkbox above the Add button — unticking it (the label then reads "— just this once") keeps a one-off find out of the catalogue while still adding the item, and each new add starts ticked again. Information items default the other way (a found letter is a one-off, not a template): `catalogChoice` in `AddItemForm` stays `null` until a player touches the box, and `toCatalog = catalogChoice ?? adv.category !== 'papers'` supplies the per-category default — ticking it still saves. Catalogue picks that are merely adjusted never save; entries live in state (`custom`, same `CatalogItem` shape); they outrank SRD entries in autocomplete, appear under Browse's ✦ Custom tab (with delete), and upsert by name (`saveCustomItem`/`deleteCustomItem`).
- Item icons: derived at display time (`itemIcon`/`defaultIcon` in `src/types.ts` — name rules, then subtype, then category), stored on the item only when a player overrides via the editor's icon button (`IconPicker`, generalized with `title`/`presets`).
- Item photos: `item.image` holds a small JPEG data URL compressed client-side (`src/image.ts`, ~1000px/0.72 with a 640px retry, ~300 KB target); attach/replace/remove in the editor, thumbnail + tap-to-zoom in the detail view. `save()` turns a storage-quota failure into a friendly error.
- Spell compendium: `src/spellIndex.ts` (name index + `SpellRef` type + `findSpellInName`) ships in the main bundle; `src/spells2014.ts` (all 319 SRD spells, 2014 text, generated from DM-Screen's `src/data/spells2014.js`) is dynamically imported as its own chunk the first time a card opens (`loadSpells` in `SpellCard.tsx` caches it for the session). A quiet 📖 button fixed in Home's lower-right corner opens `SpellCompendium` (browse all 319 grouped by level, C–9 level chips, search by name — 3+ chars also greps spell text into a "Mentioned in the text" section — tap a row for its `SpellCard`). Party spellbook: player-entered spells (owned paid content, homebrew) live in state (`spellbook: SpellRef[]` — one more collection in the same blob a future server would sync; all writes via `saveSpell`/`deleteSpell` in api.ts, logged). `src/spellbook.ts` stamps them into module state at load (`applySpellbook`, applyHolderNames-style) and exposes the merged lookups (`spellKnown`/`spellDisplay`/`customSpell`/`allSpellNames` + a `spellbookStamp` that invalidates `tokenizeSpells`' cached regex) — spellLinks, StatFields autocomplete/✓, ItemDetail links, and SpellCard all consult them, with custom entries winning name collisions. In the compendium, custom rows are marked ✦ with an ✎ edit button, ＋ Add spell lives in the modal head, and an empty search offers to add the query; the editor composes the same meta string format the SRD uses ("Level 3 Evocation (Bard)"), parsed back on edit by `levelOf`/`schoolOf`/`classesOf`. The shipped bundle stays SRD-only — paid content exists only in the party's own storage. In an item's spell list, names the index knows render as dotted-underline buttons opening the card; unknown (homebrew/paywall) names stay plain text. Matching lives in `src/spellLinks.ts` (hand-written): scrolls match a known spell anywhere in the item name; other items only after " of " ("Wand of Fireballs", plural-tolerant, longest match, skipped when the item has its own spells list) — either way a 📖 lookup button lands on the Spell row. `tokenizeSpells` also links spell names inside detail-view notes, but only in the compendium's exact casing ("Magic Missile", not "magic missile") so common words in prose stay plain. Known names render in the accent color. The Spells stat control (`SpellsField` in `StatFields.tsx`) is structured rows — name input (compendium autocomplete chips; completing focuses the cost field) + charge-cost number + ✕, a ＋ Spell button, and a live ✓/? mark per row — but serializes to the same "Name — cost" text lines in `stats.spells`, so storage/casting/cards are untouched. The charges + spells pair is offered on every category except consumables/papers/treasure (advanced where not already primary — Luck Blade, Instrument of the Bards). Regenerate the two generated files together rather than hand-editing.
- Conjured spell scrolls: typing "scroll of …" in the add box synthesizes a catalogue entry per matching spell (`src/scrolls.ts`), so all 319 exist without being stored — the names already ship in `spellIndex.ts`, and a packed `SPELL_LEVELS` digit string (~170 B gz) supplies level, SRD rarity, and the spell scroll table's save DC / attack bonus. Picked scrolls arrive as consumable/scroll with `stats.spell` set (so the detail view links to the card) and never join the party catalogue. Deliberately invisible elsewhere: not in Browse, not in ordinary searches, and party spellbook additions get scrolls for free.
- Item catalogue: `src/catalog.ts` holds ~396 SRD items: 253 generated from the DM-Screen project's item list (weapons/armor/magic, enriched with SRD attunement flags and standard weights) plus the 2014 mundane equipment (143 entries with `value` prices in two marked blocks: the adventuring-gear table, then packs/instruments/artisan's tools/focuses/clothes/ammunition/tack). It powers the quick-add autocomplete and the 📖 Browse modal (`CatalogBrowser`); picking an item prefills the advanced fields, value included. Catalogue entries can carry `freshness` (long rests of shelf life — Goodberry: 1, "gone by morning"), prefilled into the add form by `applyCatalog` when the entry is picked; a bare typed name stays bare, as it does for every other catalogue field. One-off data fixes inline are fine.

- Motion: CSS-only animations live in the `---- motion ----` block of `src/styles.css`; a `prefers-reduced-motion` override at the end of the file collapses all animation/transition durations. Change-driven triggers must never replay on the 10 s poll: the Senchez gulp and attunement shimmer compare against a ref of the previous value, the new-item glow keys off `createdAt` age (< 4 s), charge pops remount via `key={charges}`, and the gold count-up (`useCountUp` in `GoldTracker.tsx`) animates only when the total changes. Journal tear-out delays the actual delete by 300 ms so the exit animation can play. Ambient quirks: Senchez idle-fidgets on a 2–5 min random timer and "oofs" (with badge sag) when ≥25 lb lands at once; cursed items' collapsed cards glitch for ~0.8 s (skull + desaturation + gray shell, one-shot animations) on a JS timer at a random 15–75 s interval re-rolled per burst (`cursing` in `ItemRow`); the detail Cursed row re-flickers every ~9 s; empty lists get a hand-drawn SVG tumbleweed pass every 5–10 s (random, `Tumbleweed.tsx`); Home results cascade via :where() so exit animations still win specificity ties.

## Conventions

- Keep it dependency-light. Don't add a database, state library, or auth library without being asked.
- Sandbox note: don't `pkill -f 'node server/index.js'` in scripts whose own command line contains that pattern.
